# مزامنة العملاء والموردين

المرحلة الحالية للبطاقات الجديدة ذات `cust_id` و`acc_id` المحجوزين من `SyncReserveEntityId` للفروع 1..999. البطاقات القديمة تبقى محلية في مسجل رصيد، والمعرفات من نطاق القاعدة المستقلة 1000 لا تدخل هذه المرحلة. يجب تخصيص رمز فريد لكل قاعدة فرع، وعدم تصفير العدادات، ووجود الحسابات الآباء وأنواع الأسعار نفسها في قواعد الاستقبال. لا تعالج هذه المرحلة تعارض نطاقات قديمة أو دمج قواعد مستقلة.

## الملفات

- `CustomerSyncContract.cs`: أسماء الحقول، وفحص الحزمة والهوية والنطاق.
- `CustomerApplyEngine.cs`: التطبيق المشترك بين API واستقبال RasidSync؛ النسختان متطابقتان باستثناء namespace.
- `LocalCustomerApplyService.cs`: يفتح قاعدة الفرع ويطبق الحدث دون إعادة تسجيله للإرسال.
- `CustomerPackageService.cs`: إنشاء استبدال من النسخة المحلية، وفحص حركات الحذف المحضّرة قبل الإرسال.
- داخل رصيد: `Sync2/CustomerSupplierSync/CustomerSyncRecorder.cs` يسجل الإضافة والتعديل ويحفظ حزمة الحذف قبل إزالة البطاقة.

## الحزمة والحركات

`entity_type = CustomerSupplier` للعميل والمورد معًا؛ `cust_type` يحدد 1 عميل و2 مورد. JSON يحتوي `Version=1` و`Customer` و`Account` و`Metadata` للعرض. `entity_uuid` GUID ثابت مشتق من `cust_id` الجديد بصيغة `43555354-0000-0000-0000-{cust_id:D12}`؛ لا نضيف حقل UUID إلى البطاقة ولا نغير معرفاتها. `event_uuid` جديد لكل حركة.

| العملية | التطبيق |
|---|---|
| 1 إضافة | إضافة الحساب والبطاقة أو تحديث النسخة الموجودة ذات الهوية المطابقة |
| 2 تعديل | تطبيق نسخة كاملة بالهوية نفسها، ويمكن إنشاؤها إن كانت مفقودة |
| 3 حذف | فحص الاستخدام ثم حذف البطاقة وحسابها؛ غيابهما نتيجة ناجحة |
| 4 استبدال | نسخة حالية جديدة؛ تحدث أو تعيد إنشاء السجلين عند غيابهما |

`acc_id` و`cust_id` و`acc_no` و`acc_perent_no` محفوظة من المصدر. تغيير ربط البطاقة أو نوعها أو رقم الدليل أو الأب لحساب موجود يرفض بتعارض واضح قبل الكتابة. لا نحذف ثم نعيد إدخال حساب موجود في الاستبدال. `acc_debt` و`acc_credt` و`acc_balance` لا ترسل؛ يبدأ الحساب الجديد بصفر وتبقى القيم المحلية للحساب الموجود كما هي.

## الفشل والتكرار

التطبيق يفحص الحقول والأب ونوع السعر ورقم الدليل وربط البطاقة قبل الكتابة، ويستعمل قفلًا مسمى للقاعدة بين مسارات مزامنة العملاء. `tbl_sync_customer_applied` جدول مستقل ينشأ تلقائيًا في كل قاعدة مستقبلة لتسجيل `event_uuid` وبصمة الحزمة بعد التطبيق. إعادة الحدث نفسه لا تعيد بيانات أقدم فوق تعديل أحدث. لا تحذف هذا الجدول أثناء التشغيل. حساب قاعدة البيانات يحتاج صلاحية CREATE إضافة إلى القراءة والكتابة.

الـAPI ينشر الحركة للفروع بعد نجاح التطبيق فقط. أخطاء البيانات تعزل بالطابور الحالي؛ أخطاء الاتصال وانتهاء انتظار القفل توقف الدورة لإعادة المحاولة. الاستقبال لا يسجل حدث إرسال جديد. قبل الحذف نفحص القيود، والأرصدة، والأبناء، والبطاقات الأخرى، ومراجع الأعمدة المعروفة وأي FK صريح؛ وجود ارتباط يرفض الحذف. الأسماء غير القياسية في جداول إضافية تحتاج إدراجها في قائمة فحص المراجع.

مع MyISAM لا ندعي وجود Rollback. إذا فشل إدخال البطاقة بعد الحساب، تبقى البيانات الجزئية لتصلحها إعادة الحدث. وبعد حذف جزئي في الاستقبال تعاد محاولة الحذف مع إعادة فحص الارتباطات.

مسجل رصيد يحفظ حذفًا بحالة إرسال 1 قبل التنفيذ، ويحوّله إلى 0 بعد تأكيد غياب البطاقة والحساب. قبل الإرسال يفحص RasidSync هذه الحركات: إذا غاب السجلان يفعّلها؛ إذا بقيا يلغي الحدث المحضّر فقط دون حذف بيانات؛ والحذف الجزئي يعزل بالحالة 5 للدعم. لا يكمل حذفًا جزئيًا محليًا تلقائيًا. تسجيل الإضافة أو التعديل بعد الحفظ قد يفشل؛ رصيد يعرض تحذيرًا صريحًا، ويمكن إعادة تسجيل البطاقة عبر `TryRecordCustomer(id,4,out error)` بعد معالجة الخطأ.

قفل المزامنة لا يغير توليد `acc_no` داخل شاشة الإضافة. حماية رقم الدليل من جهازين يحفظان في الفرع نفسه، أو من أي مسار خارجي لا يستعمل القفل، تبقى خطوة مستقلة. خدمات العميل ليست جزءًا من حزمة البطاقة الحالية. لم نعدل الجوال أو تطبيق الفواتير والسندات.

## تجربة على نسخ قواعد منفصلة

حدّث API وRasidSync معًا قبل تسجيل أول حركة عميل؛ الإصدارات السابقة تتجاوز النوع غير المدعوم. ثبت ملف المسجل داخل مشروع رصيد واستبدل شاشتي الإضافة والعرض بالملفين المرفقين. احتفظ بالآباء تحت أرقام الدليل نفسها وبأنواع الأسعار في قواعد الفروع.

1. أضف عميلًا ثم موردًا؛ افحص حركة 1 في `tbl_sync_send` وظهور البطاقة والحساب على السيرفر والفرع الثاني بالمعرفات نفسها.
2. عدّل الاسم والمعلومات؛ افحص حركة 2 والاسم في الحساب والبطاقة.
3. من سجل الإرسال الناجح استخدم «إعادة مزامنة المستند»؛ يجب أن تظهر حركة 4 جديدة دون تعديل القديمة.
4. احذف بطاقة دون قيود أو رصيد؛ افحص حركة 3 وغياب السجلين في الجهات المستقبلة. جرب منع حذف حساب مستخدم.
5. أعد إرسال الحدث نفسه؛ لا تتكرر البطاقة أو الحساب. جرب تعارض رقم دليل لتظهر حركة معزولة دون الكتابة فوق الحساب الآخر.

## الفحص الآلي

`Tests/CustomerSupplierSync` يختبر الكود الفعلي على MySQL 5.7 وMyISAM، بما يشمل الحركات الأربع والتكرار والأرصدة والتعارضات وفشل إدخال وحذف جزئي عبر triggers وتنافس رقم الدليل. الاختبار لا يعمل إلا في قاعدة اسمها `customer_sync_test` ويمسح جداول الاختبار فيها. إعداد اتصال الاختبار في `CUSTOMER_SYNC_TEST_CONNECTION`. ملف GitHub Actions يبني المشروع ويشغل الاختبار في قاعدة مؤقتة.
